# Agent 与大模型技术热点｜2026-11-20

> 主观察窗口：北京时间 11 月 19 日 09:30 至 11 月 20 日 09:30。精选 5 条公开一手材料，按实际证据区分近期发布、预告与近 7 日补充。仅有日期而没有时间、时区的来源，不宣称精确落在 24 小时窗口内。未运行模型或复现论文，不将厂商成绩等同于独立验证。

## 今日主线

**Agent 的效率优化正从“换一个更强模型”，转向三个位置：模型内部的计算与缓存、工作流中的决策分工，以及工具侧的动作与权限边界。** 这是本期的综合观察，不代表所有方案已经具备生产成熟度。

## 1. Olala mini：混合 Mamba / 注意力架构，把小模型的缓存负担降下来

**日期与状态：** OVH 于 11 月 17 日预告，计划 19 日正式发布；本次已读到公开模型卡与权重页面。未取得首次公开提交时间，因此不将“首次开放下载”精确归入本期 24 小时窗口。

模型卡列出约 **6.8B 总参数、每 token 约 1B 激活参数**，36 层中包含 29 层 Mamba-3 与 7 层注意力，各层后接 MoE 模块。只有注意力层保存 KV Cache。当前上下文是 **32K**，128K 是后续计划，不是现有能力。权重采用 Apache 2.0。

**为什么值得看：** 它展示了一条不同于单纯缩小 Transformer 的路线：通过混合架构减少需要随上下文增长的缓存部分，并保留工具调用与推理能力。

**边界：** 激活参数少不代表只需存储 1B 权重，也不能直接推出固定延迟收益。模型卡明确提示默认托管推理引擎不能加载该架构，需要适配容器或相应实现；不要把平台自动生成的通用启动示例当作兼容性验证。

来源：[OVH 官方预告](https://corporate.ovhcloud.com/asia/newsroom/news/ovh-olala-mini/) · [官方模型卡](https://huggingface.co/OVHaiLLM/Olala-v1.0-mini-7A1B)

## 2. AWS Aurora：让 Agent 的工具能力具备“单向权限”

**日期与状态：** AWS 官方文章标注 11 月 19 日，正文宣布新能力可用；未提供精确时区和发布时间。

Aurora PostgreSQL express configuration 新增将现有集群迁入 VPC 的操作，保留数据和端点，不必由 Agent 协调新建集群、数据迁移与端点切换。官方同时给出一种权限设计：允许角色迁入 VPC，通过显式拒绝权限阻止其迁回互联网接入模式。

**为什么值得看：** 关键不是又多了一个 MCP 工具，而是把复杂任务收敛成较小的动作接口，并在云端权限层约束方向。即使模型产生错误计划，工具权限也不必允许对应动作。

**边界：** 端点不变不等于无中断，已有连接会断开并需要重连；仍需准备私网连通性，并由人确认目标网络及变更时机。工具等待超时也不代表底层变更已经取消。

来源：[AWS 官方发布与 Agent 工具说明](https://aws.amazon.com/blogs/database/from-instant-aurora-postgresql-databases-to-production-ready-in-your-vpc/)

## 3. Gemini 4 Neon：关注长流程编排和多模态工作，而不只看榜单

**日期与状态：** 11 月 18 日发布，作为近 7 日补充，不算本期新增。官方宣布向 Gemini API、企业入口及符合条件的付费产品用户推出。

官方列出 **100 万 token 上下文**，支持在同一上下文处理文档、图表、音频与视频等材料；强调工具密集任务、长会话压缩，以及在 Antigravity 中协调 Hydrogen 子 Agent。标准价格为每百万输入 / 缓存输入 / 输出 token **3 / 0.15 / 15 美元**。

**为什么值得看：** 模型产品定位进一步围绕“完整工作流”展开，协调者、执行者和上下文管理不再是互不相关的能力。

**边界：** 官方展示的成绩受推理设置及 Agent 执行框架影响，不能把框架增强后的分数当成裸模型收益；本期未独立复现，也未验证特定账户的开放状态。

来源：[Google 官方发布](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/)

## 4. DaisyRose-27B：长任务训练，不等于扩大单次上下文

**日期与状态：** 开发团队 11 月 18 日发布，近 7 日补充。已发布 BF16、FP8、NVFP4 权重，采用 Apache 2.0。

该模型基于 Qwen3.8-27B，通过强化学习训练长流程 Agent。团队披露约 1,200 个精选任务、144 张 H200、18 天训练，并报告 Terminal-Bench 4.1 pass@1 从 5.6% 升至 12.0%。

容易误读的是“训练会话最长 100 万 token”：**模型上下文仍为 256K**，长会话依靠执行框架摘要跨越多段轨迹。它保留基座的架构、图像理解与聊天模板，而不是重新训练一个 100 万上下文架构。

**为什么值得看：** 按基座具体错误设计任务、提供长交互环境，是改进 Agent 能力的一条可追踪路线。

**边界：** 成绩由开发者报告，表格逐项取 BF16 与 FP8 结果中较高者；不能据此断言任何部署精度都得到同样收益。

来源：[开发团队技术文章](https://huggingface.co/blog/RadixArk/daisyrose-27b-pushing-the-frontier-of-post-trainin) · [模型卡](https://huggingface.co/RadixArk/DaisyRose-27B)

## 5. AnyS1：把“大模型每一步都思考”改成有条件分工

**日期与状态：** 预印本于 11 月 18 日 03:05 UTC 提交，即北京时间 11:05，属于近 7 日研究补充。

AnyS1 从公开技能说明中抽取可以枚举候选项的决策点，用容器内执行轨迹训练一个 4B 决策模型。运行时，普通选择由小模型一次前向完成；置信度不足时再交给大模型，开放式生成并非全部替换。

作者在三个未见基准上报告，相比未编译的大模型 Agent，任务调用成本下降 75%–91%，模型调用时间下降 63%–92%。

**为什么值得看：** 优化对象从“整次请求选择哪个模型”，细化到“同一工作流中哪些节点可以交给小模型”。

**边界：** 时间指标主要统计模型调用链，不等于包含工具执行和网络等待的完整业务耗时；收益取决于可枚举决策占比及置信度校准。尚不能把论文标题中的“任意工作流”理解为已经普遍验证。

来源：[论文及提交时间](https://arxiv.org/abs/2611.23751) · [正文与测量协议](https://arxiv.org/html/2611.23751v1)

## 两点判断

1. **选型需要拆开三个量：模型上下文长度、Agent 会话累计长度、完整任务耗时。** 三者经常同时出现在发布材料里，但不可互换。
2. **更可控的 Agent 应同时具备能力分工与权限边界。** 小模型接管确定性较高的选择，大模型处理开放式推理，工具服务限制可执行动作。前两者改善效率，后者降低误操作的影响范围，不能彼此替代。

本期不重复昨日的 GPT-6.2、AssemblyAI 和冲突记忆论文，也不以未经核验的社交热度或部署效果补足条数。
