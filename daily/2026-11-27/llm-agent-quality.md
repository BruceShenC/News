# 大模型与 Agent 质量、测试与工程资讯｜2026-11-27

观察窗口：11 月 26 日 09:00 至 11 月 27 日 09:00（北京时间）；较早材料单独标注。测试结果来自公开报告，未在本地复跑。

**本期重点：能加载不等于能续训，KV 命中不等于能复用。** 两类问题都适合用故障注入加对照组，把验收推进到真正需要成功的下一步。

## 训练质量

1. **Unsloth：一次失败的分片保存，不应毁掉上一份可恢复检查点。** [#19705](https://github.com/unslothai/unsloth/pull/19705) 11 月 26 日合入主分支，未核实稳定版收录。原行为会原地覆盖 FSDP2 的 DCP 优化器分片。作者用 tiny Llama、双 CPU rank（Gloo），在已有有效检查点上让 rank 1 写到一半失败。修复前后两个 rank 都报错，但旧版分片哈希改变、无法恢复，修复后旧分片逐字节不变、恢复状态逐位一致。另测了两次目录重命名之间中断后恢复完整的新一代状态。四个新增用例在旧版失败、补丁版通过；[测试入口](https://github.com/unslothai/unsloth/pull/19705/files)是 `test_fsdp2_native_ckpt_write_failure_gloo.py`。这不证明双 GPU NCCL 或真实多机本地盘通过；作者指出节点依次切换时仍可能出现代次分裂。**建议门禁：所有 rank 恢复到同一代，并用同一批样本验证首步权重更新。**

2. **verl：权重加载完全正确，第一次优化器更新仍可能把模型拉回初始状态。** [原始 Issue #8604](https://github.com/verl-project/verl/issues/8604)；[11 月 26 日开放 PR #8862](https://github.com/verl-project/verl/pull/8862)。触发条件是 Megatron 只恢复模型、不恢复优化器，低精度模型权重更新了，FP32 主权重却未同步。作者在 RTX 4090 上用 Qwen2.5-0.5B 跑两步、保存、重新初始化后按 `["model","extra"]` 加载，再跑一步。修复前后刚加载时与检查点的权重 L2 距离均为 0；首步后，距检查点从旧版的 64.40 降到补丁版的 2.16。作者还报告旧版 4 个可比 GPU 用例失败，补丁版这 4 项加另外 3 项通过。尚未合入。**验收时用“同样新建优化器”的对照来比首步更新**，不要把只载模型与完整断点恢复混为一谈。近期相关：[Miles 草稿 #5059](https://github.com/radixark/miles/pull/5059) 用单机 8×H200 的 LoRA 实验发现，训练步数继续推进时数据游标可能回到开头，因此还要核对恢复后实际消费的样本 ID。

## 推理质量

3. **SGLang：全量注意力 KV 命中 192 token，实际可用前缀却为 0。** [Issue #53149](https://github.com/sgl-project/sglang/issues/53149) 来自 DGX Spark/GB10 上 Inkling-2-Mini 的 24 路约 72K token 多轮负载。报告者在逐请求记录里发现，滑动窗口所需的缓存行被淘汰，使部分二轮请求即使全量 KV 命中，也要重新预填充。报告者的同配置小样本对照中，刷新缓存后两轮各 0 次未复用，对照三轮分别 9、10、10 次，二轮 TTFT 报告为 3 秒对 163–186 秒；这是该配置的结果，不是通用延迟提升。[开放 PR #53315](https://github.com/sgl-project/sglang/pull/53315) 将场景缩成 192 token 前缀、64 token 页、128 token 滑窗跨两个节点，再驱逐一页。作者报告 Python/Rust 两种缓存树、5 和 256 token 两种回复均从复用 0 恢复到 192，全量 KV 命中始终为 192；PR 作者没有复跑原 GPU 首 token 延迟（TTFT）负载。**线上探针建议：同长度冷请求、低负载热请求、并发热请求三组对照，分别看逐请求实际复用比例、TTFT 和固定答案；缺失缓存字段不能记为零。**

4. **SGLang：防止预填充超配，也要防止有容量却一直不调度。** [11 月 26 日开放 PR #53397](https://github.com/sgl-project/sglang/pull/53397) 的作者在 RTX PRO 5000 用 6,144 token KV 池、64 token 页做前后对照：旧版接纳 6,144 token 续块后解码分配失败；补丁将续块缩到 6,080 token，留出一页，分配与后续解码成功。严格 8,192 网格装不下时，补丁让请求等待而不是超配。作者报告 CPU/GPU 各 126 个单测通过，[测试入口](https://github.com/sgl-project/sglang/pull/53397/files)是 `test_prefill_adder.py`，不是整模吞吐验证。评审另指出分片开销和已持有滑窗资源可能造成过度拦截，尚不是复测结论。**门禁两侧都要测：放不下时不超配；有合法更小续块或可复用资源时必须能继续。**

## Agent QA 工具

5. **Langfuse Topics 公测：适合发现「误报完成」，不适合判定某次任务已完成。** 近期补充，11 月 24 日发布；Cloud 全区、自托管 v4.86.0+。[公告](https://langfuse.com/blog/introducing-topics) · [文档](https://langfuse.com/docs/observability/features/topics)。它聚类已采集的追踪记录；实时视图默认在最后一次收到事件后等 10 分钟再开始分析，主题每日更新。建议让主 Agent 在三组样本里说同一句“已完成”：子 Agent 确实结束且产物可读、完全未执行、终态事件延迟到达。验收独立核对实际子任务输入、终态输出与同次运行的产物；晚到证据在可读前记作待确认。三组是验收对照，不足以评估聚类。若试聚类，用合成数据；摘要模型会收到所选追踪的完整输入输出，Cloud 计量与模型费用分开。此方案未实测。

**优先验证：** 训练侧先做「写失败后首步续训」，同时验证旧检查点与续训结果；推理侧先做「并发热缓存探针」，因为聚合命中率可能掩盖少数慢请求。
