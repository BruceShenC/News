**1. vLLM：异步 GPU→CPU 元数据拷贝，可能把“请求仍在运行”变成永久无进展**

**报告日期：11 月 1 日 20:15。** 作者报告 KV-sharing fast prefill 在异步调度下挂起：GPU 利用率 100%，请求停在 Running，没有显式错误。其排查用 faulthandler 定位到 Gemma4 fast prefill／FlashInfer 调用，再对 CPU 元数据做同步前后差分：160 步中 20 步不同；实际长度均为 1，过早读到的长度却可达负数或十亿量级。最初如何遇到故障、是否来自生产流量，未明确披露。

- **环境与入口**：vLLM 0.30.0、FlashInfer 0.6.18.post1、单 B200、Gemma4 E4B 微调模型、bf16；开启 --kv-sharing-fast-prefill --enable-prefix-caching，默认异步调度，无 speculative decoding。原报告给出调用路径和配置矩阵，另检查 main 5d55ef1。
- **怎样检出**：约 3.16 万条请求、并发 96、max_tokens=1、输入约 600—4500 token；用固定的 4649 条切片对照不同图执行模式。fast prefill 配合多种模式均挂起，关闭 fast prefill 或异步调度则完成。另给出无模型思路：用 torch.cuda._sleep 延迟 stream，调用元数据构造后立即读 CPU，预期 [0,2,3,6,7] 却读到零。
- **根因与修复边界**：报告指向 to("cpu", non_blocking=True) 返回后主机立即消费尚未完成拷贝的数据。未附完整无模型脚本、请求语料或微调权重入口，不能称“开箱即复现”；未见该报告提供完整修复后的回归结果。
- **可迁移测试建议**：把“请求完成／进度持续推进”作为判定条件，叠加人为 stream 延迟和元数据同步前后对照；不能以 GPU 忙碌判断系统健康。以上建议不是本简报已执行结果。

**2. SGLang／ROCm：同种子图像不一致，被缩小到特定构建与特定形状的 SDPA**

**报告日期：11 月 2 日 06:15。** 作者从 Qwen-Image 2.1 固定提示、种子重复生成结果不同入手，比较中间张量哈希，发现 DiT latent 一致而 VAE 输出不同，随后拆分算子定位。这是“端到端异常→中间结果→最小算子”的有价值排障链。

- **环境与触发**：单 gfx1100／W7900 类 GPU，ROCm 7.2.1 镜像中的 PyTorch 2.9.1+rocm7.2.1.lw.gitff65f5bc。固定 seed=1015、30 步、1024×1024 时约 12% 像素有差异，最大 4/255、PSNR 约 62 dB；1344×768 对照可逐位一致。这是像素可复现性问题，不等于作者证明了明显感知质量下降。
- **最小入口与判定**：ROCm 上游报告附完整脚本：固定 CUDA generator seed=0，生成 bf16 Q/K/V，形状 [1,1,4096,1152]，重复调用 math SDPA，用 torch.equal 比较。20 次均出现差异；序列长度改为 4032 则 0/20。两个独立 bmm 对照也可重复，不能直接归咎矩阵乘法。
- **前后验证**：作者启用 torch.use_deterministic_algorithms(True, warn_only=True) 后 0/20 不一致；其他 ROCm 官方／nightly 构建亦未复现，包括另一个 HIP 7.2 构建。因此不能泛化为“所有 ROCm 7.2 都坏了”。显式 fp32 softmax 对照可重复，但与 SDPA 存在约 2e-3 最大绝对差，不应拿它当通用容差。
- **限制**：底层责任组件及正式修复未确认；性能代价未披露；上游 SGLang main 仅做代码检查，不能等同在那里完成端到端复现。确定性开关是全局设置，服务中切换需考虑并发与恢复原状态。

[SGLang 端到端定位](https://github.com/sgl-project/sglang/issues/47801) · [ROCm 最小脚本、构建与形状对照](https://github.com/ROCm/pytorch/issues/3931)

**4. PyTorch：KL 损失数值正常，反向梯度却全部 NaN**

**报告日期：11 月 2 日 05:36。** 这对非法动作屏蔽的强化学习、带填充词表的蒸馏尤其相关：只监控 loss 是否有限，会漏过进入优化器前的梯度损坏。报告首次如何发现未披露，证据来自最小反向计算和解析梯度对照。

- **环境与最小输入**：PyTorch 2.15.0+cpu、Python 3.13、Linux CPU。原文完整脚本令 Categorical 的 p logits 为 [0.5,-1,2,-inf]，q 为 [0,1,-0.5,-inf]，计算 kl_divergence 并求 p 的梯度。
- **预期与实际**：KL=1.1964701414108276，前向正确；预期梯度约 [-0.2583,-0.1554,0.4137,0]，实际每一项都是 NaN。OneHotCategorical 走同一路径。源代码先产生含非有限值的乘积、再把前向结果置零，并未消除反向中的无效运算；事后 torch.where 也不够。
- **修复前后证据**：作者在本地运行时应用“乘法前屏蔽非有限因子”的补丁，对两种分布、单侧／双侧 mask、零概率和 256×362 的随机 masked batch 做对照；报告前向保持一致，梯度对 float64 解析参照的最大误差约 2.9e-8（示例）／6e-8（batch）。这是作者本地验证，不是项目已合入修复。
- **适用限制与测试建议**：未提供 GPU、完整训练收敛验证。建议同时断言 loss 与梯度有限，并检查被屏蔽位置梯度为零、未屏蔽子分布结果一致；不要把损失正常当作训练链路正常。

**5. AI 辅助数值测试：高置信度交叉熵的微小损失与目标梯度被舍入为零**

**报告日期：11 月 1 日 20:28。** 作者在审查既有 softmax-collapse 修复时，继续检查分块 F.linear_cross_entropy；披露详细复现与测量由 AI 助手协助准备、本人审阅。这是测试设计与数值参照应用，不是独立评估 AI 测试效能。

- **环境特别注意**：“current”基线是 PyTorch main 7e70f12 **已叠加 #202049 补丁栈**，不是未修改 main；显示版本 2.16.0a0，Ubuntu 26.04.1、Python 3.14.8、CUDA 13.4、RTX 5060 Ti。
- **最小测试与判定**：原文完整脚本用 W=eye(3)、logits=[9,-9,-9]、target=0，以 float64 的 log1p 解析值作参照。预期 loss≈3.046e-8、目标梯度≈−3.046e-8，实际两者为零；非目标梯度未全消失。不能笼统说“所有梯度为零”。
- **规模化与修复验证**：作者另测 N=2048、H=2048、V=128256、target margin=30；loss／输入梯度的中位相对误差由约 1.00／1.01 降至 1.26e-5。提议排除目标项求和，改用 log1p/expm1 与避免相消的目标梯度公式。已有测试修复前后都通过，说明缺少高置信度边界行；新测试与补丁栈仍是报告中的拟议内容。
- **限制**：作者单卡测得时间差在 0.3% 内、峰值显存不变，不能推广为各硬件“零成本”。H100/B200/GB300、MPS/XPU、torch.compile 未测；fp16 compact 仍有下溢限制，也没有端到端训练收益证明。建议用数学参照而非另一种同样相消的实现作判定器。

**6. AI 辅助基准核查：vLLM Rust 与 Python 客户端同名参数，却不一定施加相同负载**

**报告日期：11 月 1 日 09:59。** 报告披露由 Claude Code 协助准备，人工审阅并本地运行；通过 mock OpenAI server 记录实际请求，发现 Rust vllm-bench --output-len 对 ShareGPT／Hugging Face 数据集未按 Python 路径生效。这直接影响基准可比性，而不是模型本身质量下降。

- **复现条件**：当前 main，但未披露精确提交 SHA／运行时版本；无需 GPU 或真实模型。命令使用 openai-chat 后端、localhost mock 服务、20 条 ShareGPT 请求、--output-len 32。
- **实际请求是判定器**：预期每次 max_completion_tokens=32；Python 符合，Rust 通用参数路径却为 8—600；改用 --sharegpt-output-len 32 才恢复 32。原表同时报告总生成 token 为 640／3080／640，但这是 mock 服务实验，**不是实际模型的吞吐或生成质量测量**。HF GSM8K 也有对应偏差。
- **覆盖缺口与状态**：已有 CLI parity 测试只比较参数名，不比较负载语义。原文有命令和日志，但未附 mock 服务完整实现、ShareGPT fixture；不能声称所有人已可原样复现。报告提出统一映射／优先级方案，未给修复后验证或已合入回归。
- **建议**：跨语言基准先检查线上的请求体、输入／输出长度及并发语义一致，再比较吞吐。可用假服务做低成本契约测试，避免把负载不同误判为引擎更快。

**7. AI 辅助梯度核查：embedding 的前向 AD 与反向 AD 对 padding 不一致**

**报告日期：11 月 2 日 01:20。** 作者披露 Claude Code 辅助撰写、本人手动验证；原始发现途径未进一步说明。案例利用数学关系而不是大规模标注集发现问题。

- **环境与入口**：PyTorch 2.14.1、Python 3.12.14、M5／macOS 26.7.2 的 CPU。原文完整脚本固定 seed=0，以 float64 的 4×3 随机 embedding weight、indices=[0,2,0]、padding_idx=0，分别求 jvp 与 vjp。
- **判定依据**：按框架 padding 梯度语义，前向切向量的 padding 位置也应与反向实现一致；对随机切向量 v、余切 g，比对伴随关系 〈g,Jv〉=〈Jᵀg,v〉。作者得到约 0.9854 与 0.4710，二者明显不等，指向前向 AD 未应用 padding 的特殊处理。
- **修复与限制**：报告未给出已合入修复、修复后验证或 GPU 结果。这里检验的是前后向实现与框架定义的一致性，不能直接外推所有 embedding 梯度或所有训练都错误。
- **建议**：把前向／反向 AD 的伴随关系做成性质测试，覆盖重复索引、padding 与无 padding 对照；这些扩展是本简报建议，非作者已执行覆盖。

[完整最小脚本、数值输出与 AI 披露](https://github.com/pytorch/pytorch/issues/202956)

**本期判断与值得小范围验证的两项**

1. **先看 KL 的“前向正常、反向坏掉”测试**：CPU 最小例子、明确的解析参照，容易迁移到 RL、蒸馏及 masked loss 的回归集。验证时同时检查 loss、每层梯度、mask 不变量，暂不把报告中的本地补丁直接用于生产。
2. **先做基准客户端请求契约测试**：mock server 就能检查参数是否真的变成预期请求，成本低，能避免无效的 GPU 性能对比。应先补齐 fixture、固定版本，再复核自己的实际后端。

**共同趋势**：质量保障需要从单个最终指标下探到中间张量、梯度和请求语义；“所有现有测试通过”“固定种子”“GPU 仍忙碌”都不是充分保证。AI 可以协助生成复现和数值对照，但本期证据仍依赖人工复核及明确测试环境，不能据此宣称普遍提高测试效能或自动修复成功。
